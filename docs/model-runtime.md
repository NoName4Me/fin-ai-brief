# 模型主备切换与任务重试

本文记录当前实现的运行规则（2026-11-13），用于运维及后续设计参阅。主备切换、模型输出修正、任务队列重试是三个独立层级，不能将它们的次数混为一次重试上限。

## 配置与开关

模型管理页的「模型调用」分组包含「开启模型调用」总开关、波谷限制和每日调用上限。总开关点击立即保存，策略项通过「保存」提交。

- 总开关控制 Worker 的自动资讯处理、出刊调度、恢复探测，并在模型队列任务执行前检查。关闭后，尚未执行的任务进入等待；已经开始的请求允许完成。
- 单个模型的启用状态决定它是否参与业务调用；列表第一项是主力，其余启用模型按列表顺序作为备用。暂停项跳过，主力固定在列表首位，备用可拖拽排序。
- 总开关默认关闭。清空模型列表会在同一配置事务中自动关闭总开关；重新添加模型不会自动打开。空列表不回退到环境变量模型。
- 自动采集、模型调度、自动出刊和邮件推送分别控制。关闭自动采集不会停止对既有资讯的模型处理；关闭自动出刊也不会停止资讯处理。Worker 进程本身仍可运行。
- 手动连接测试可在调度关闭或模型停用时执行，也不受波谷限制；它仍会产生调用记录并使用每日额度。总开关并非所有底层模型 API 的统一禁用开关，直接调用模型的管理操作需以各操作实际检查为准。

update 升级时，已保存且完整的旧单模型配置迁移为主力，保留地址、密钥、模型名及该模型启停状态。旧版本没有新增的调度字段时，总开关默认关闭，升级后需手动确认并开启。已有多模型列表不会重复迁移。

## 主备调用顺序

每条业务请求从列表头开始筛选已启用、未处于不可用状态且不在冷却中的模型，按顺序调用。模型之间不做负载均衡，也不将同一请求同时广播给多个模型。

以主力 A、备用 B、C 为例：

1. 优先请求 A；成功即结束。
2. A 发生可用性错误，当前请求立即尝试 B；B 也失败则尝试 C。
3. 全部候选失败或没有候选，当前模型调用失败，由外层任务决定后续是否重试。
4. 每条新请求重新按优先顺序选模型；第一次使用备用不代表后续请求会一直跳过主力。

### 错误分类

| 情况                                                    | 主备行为                                             |
| ------------------------------------------------------- | ---------------------------------------------------- |
| HTTP 401/403、408、429、5xx，连接异常、超时等可用性错误 | 记录失败并尝试下一候选模型                           |
| 其他被归类为请求失败的错误                              | 同样尝试下一候选模型                                 |
| JSON 语法、响应结构校验、空正文、输出不完整等质量问题   | 不因此切换备用；按输出修正规则处理或交给外层任务重试 |

业务 API 单次 HTTP 请求超时上限为 180 秒。遇到超时后才进入后续处理，因此整个任务的等待时间可能包含多个模型的耗时。

## 失败隔离与恢复

以下阈值当前写在代码中，管理台暂不可调整。

| 项目                       | 当前规则                                                            |
| -------------------------- | ------------------------------------------------------------------- |
| 首次、第二次连续可用性失败 | 标记调用波动；本次尝试备用，下条新请求仍可优先尝试主力              |
| 第三次连续失败             | 标记不可用，开始 5 分钟冷却，普通业务请求跳过该模型                 |
| 持续失败                   | 冷却按 5、10、20、30 分钟增长，最大 30 分钟；按失败计数计算         |
| 业务调用成功               | 清零连续失败计数，标记健康                                          |
| 自动恢复确认               | 连续两次探测成功，探测间隔至少 2 分钟，才标记恢复                   |
| 探测内容                   | 小型聊天请求，要求返回简短正文，最多 8 个输出 token，单次超时 30 秒 |

Worker 每分钟检查需要恢复探测的模型；仅选择已启用、状态不可用、冷却已结束且满足探测间隔的模型，每轮最多检查两个。总开关关闭、没有启用模型或当日额度耗尽时不探测。恢复探测当前不受波谷限制，并计入模型调用记录及额度。

主力恢复确认后，新业务请求重新优先使用主力；已经交给备用的请求不迁移。备用也适用健康检查及恢复规则。手动连接测试成功会直接标记健康，属于人工确认，不必再等待两次自动探测。

示例：A 连续三条业务请求超时，每条由 B 接管；随后 A 进入冷却，业务直接使用 B。冷却结束后 A 第一次探测成功，业务仍使用 B；至少两分钟后第二次探测成功，新请求恢复优先使用 A。

## 三层重试的区别

| 层级                 | 触发条件                           | 次数与执行方式                                                                            |
| -------------------- | ---------------------------------- | ----------------------------------------------------------------------------------------- |
| 同一模型输出修正     | 返回 JSON 无法解析或业务结构不合格 | 通常最多调用 2 次（首次加一次修正）；顶层 facts 数量超限时最多 3 次，携带错误反馈要求修正 |
| 同一业务请求主备切换 | 当前模型发生可用性错误             | 按候选顺序尝试下一模型；不是队列重试                                                      |
| 整条任务队列重试     | 任务执行最终抛错，尚有重试次数     | 任务重新执行，默认额外 1 次，可在任务处理配置中设置 0～3 次                               |

输出截断、空正文等情况并不保证进入同一模型的 JSON 修正循环，可能直接失败并交给外层处理。一次任务中还可能有分析、复核、多个栏目生成等多个模型调用，因此「任务最多两轮」不等于「最多两个 HTTP 请求」。

## 队列重试规则

### 次数、间隔与超时

- `collect`（采集）、`process`（资讯处理）、`generate`（出刊）入队时记录当时的 `taskRetryLimit`。默认 1 次额外重试，即首次执行加一次重试，最多两轮；上限配置为 3 时最多四轮。
- 修改重试配置影响新入队任务，不重写既有任务的重试上限。
- 普通失败以 10 秒为基数，使用队列的指数退避和随机延迟；实际开始时间还受队列轮询、并发和 Worker 状态影响。
- 采集及资讯处理若被错误分类器识别为临时网络故障，改用固定 300 秒延迟、不启用指数退避。分类器检查错误及其 cause、AggregateError；未保留这些信息的包装错误可能走普通退避，不能理解为所有模型网络故障都一定等待五分钟。
- 出刊任务没有上述五分钟特殊分支，采用普通退避。
- 队列任务执行超时配置为 900 秒；超时、Worker 中断等异常由队列处理，资讯状态还由定期协调逻辑校正。
- 邮件投递、调度 tick 和清理任务的队列自动重试次数为 0；邮件还受自身投递状态与去重规则约束，不适用上述模型任务规则。

### 等待不等于失败重试

| 等待原因           | 恢复条件                                       |
| ------------------ | ---------------------------------------------- |
| 模型调度关闭       | 重新开启总开关，具备启用模型、额度及时段条件   |
| 不在允许的波谷时段 | 进入允许时段，或关闭波谷限制                   |
| 当日额度耗尽       | 北京时间跨日或提高每日额度后，重新具备剩余额度 |

等待通过阶段记录保存，队列当前轮可结束，恢复时再创建关联的新任务，不用失败自动重试来空转。波谷时间为北京时间工作日 00:00—09:00、12:00—14:00、18:00—24:00，以及周末全天；法定节假日没有独立日历，按星期处理。

### 重试耗尽与手动重试

任务重试耗尽后保留失败状态。资讯处理的文章也会被标为失败，不会无限自动入队；定期协调覆盖队列过期、Worker 崩溃等遗漏。

管理员可在任务管理手动重试：资讯先校验失败状态并锁定文章，避免同一资讯重复排队；重试创建新任务，使用当前的重试配置。采集任务的手动重试会带手动标志，可绕过自动采集总开关。模型任务的手动重试仍受模型调度开关、波谷及额度检查。

资讯处理已成功的阶段，以及相同输入、提示词与模型路由等生成的成功请求缓存，可在条件未变化时复用；不是每次重试都从头产生所有模型调用。失败请求不作为成功结果复用。

示例：默认额外重试一次，第一轮 A、B 均失败，任务等待队列退避后进入第二轮；第二轮按模型当时的健康状态选候选，仍失败则停止，保留失败供人工处理。

## 统计与排查

- `model_calls`：模型业务调用、连接测试及恢复探测记录。
- `model_attempts`：每个候选模型的尝试、异常分类、耗时与 token 等记录。
- `model_health`：连续失败/成功次数、健康状态、冷却截止及最近探测时间。
- `model_routing`：最近调用路由；总览按当前配置和可用优先顺序计算模型，不直接把历史路由当成仍在运行的模型。
- `model_events`：配置修改、启停、主力变更、故障切换及恢复事件。
- `pgboss.job` 和 `processing_steps`：整条任务的执行/重试及各处理阶段。

模型运行记录页提供当前周期异常分布和运行事件；任务管理展示整条任务及阶段执行情况。模型异常和事件默认保留滚动 7 天，随系统设置的数据清理执行，并非每周固定某天一次清空；当前自动清理计划为北京时间每日 03:20，关闭自动清理则不执行删除。
